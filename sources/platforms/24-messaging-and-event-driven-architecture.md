# 24. Messaging and Event-Driven Architecture — brief and source ledger

## Brief

- **Hook.** A consumer of the fills topic crashed after applying a batch of messages and before recording how far it had read; when it restarted it applied the batch again, and the firm's position in one stock was double for eleven minutes. The messaging system had delivered every message at least once, exactly as promised.
- **Sections.** Why systems talk through messages; Brokers and brokerless transports; The log as the backbone; Delivery guarantees and the exactly-once myth; Patterns: outbox, event sourcing, dead letters.
- **Defines.** message broker, brokerless messaging, publish--subscribe, partitioned log, consumer offset, consumer group, at-most-once delivery, at-least-once delivery, exactly-once processing, transactional outbox, event sourcing, dead-letter queue.
- **Uses (defined earlier).** idempotent processing (B13.24), sequencer architecture (B13.24), input journal (B13.23), back-pressure (B13.12), slow consumer (B13.12), multicast (B13.16), ring buffer (B13.12), position service (ch17), stream processing (ch1).
- **Tutorial.** Implement a partitioned log in process (topics, partitions, offsets, retention, consumer groups with rebalancing), publish a day of fills from firm.exchsim keyed by account, and run the position service as a consumer under a crash schedule in three modes -- commit before processing, commit after, and idempotent processing with the offset stored atomically with the state in SQLite; add a transactional outbox to the trade-capture service. End state: lost and duplicated fills per mode over many crash schedules, and the position error each produces.
- **Build.** `firm.eventlog`: `Log` with topics, partitions by key hash, append-only segments on disk, offsets, retention, consumer groups with rebalance; producer with idempotence keys; consumer helpers for the three delivery modes; an outbox table and relay on the standard library's sqlite3; a dead-letter topic; Python, no server.
- **Weekend problem.** Double for eleven minutes -- named result: duplicated and lost fills per thousand crashes under at-most-once, at-least-once and idempotent-with-atomic-offset processing, and the maximum position error each produces.
- **Facts to verify.** Kreps, Narkhede and Rao 2011, Kafka: a distributed messaging system for log processing (NetDB); Apache Kafka documentation: delivery semantics, idempotent producer and transactions (dated); Kleppmann 2017, Designing Data-Intensive Applications (O'Reilly); ZeroMQ guide (brokerless patterns); Aeron documentation (brokerless reliable UDP messaging, used in trading).
- **Data.** firm.exchsim fills; synthetic crash schedules.
