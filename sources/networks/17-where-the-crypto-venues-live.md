# 17. Where the Crypto Venues Live — brief and source ledger

## Brief

- **Hook.** Most of the largest crypto venues do not run their matching engines in an exchange data centre but in one public cloud region, and several say so; a firm that wants to be close launches machines in that region, measures, and keeps the few that happen to sit nearest the venue's servers.
- **Sections.** The publicly known locations; How to discover a location; The instance lottery; Continuous re-measurement.
- **Defines.** autonomous system, anycast, edge network, round-trip triangulation, instance lottery.
- **Uses (defined earlier).** cloud region (B3.26), availability zone (ch16), availability-zone identifier (ch16), geodesic distance (ch10), latency floor (ch10), group index (ch10), route factor (ch10), centralised exchange (B3.15), dedicated endpoint (B3.25), cusum test (B7.13), placement group (ch16).
- **Tutorial.** Match endpoint addresses against a provider's published IP-range file (a fixture in the documented format), estimate a server's location by round-trip triangulation from probes at known sites (constrained least squares with the fibre light-time as a bound), and simulate the instance lottery -- the expected best round trip among n instances and the cost of the search -- with parameters from cited figures, labelled as a simulation. End state: a best-of-n chart against launch cost and a triangulation example.
- **Build.** `firm.venuefind`: a CIDR prefix matcher over published IP ranges, round-trip triangulation on firm.geomap, an instance-lottery planner (order statistics, optimal number of launches for a value per microsecond), and a re-measurement scheduler that flags a venue move with Book 7's CUSUM test (firm.decay, wrapped); Python. Consumed by chapters 18, 19 and 29.
- **Weekend problem.** Launch forty, keep one -- named result: the expected best round trip among n instances and the number of launches that maximises value per microsecond net of launch cost.
- **Facts to verify.** venue documentation or firm publications stating a venue's cloud region or data centre (AWS case studies, venue blogs, venue API docs) (dated box, each row sourced); Glassnode research reported by CoinDesk (March 2026) on Hyperliquid validators in Tokyo (dated); a venue's disclosed move of its infrastructure between regions (e.g., BitMEX Dublin to Tokyo, 2025) from the venue or quality press (dated); AWS ip-ranges.json documentation; RFC 4786 (operation of anycast services); AWS blog 'Ultra-low-latency cross-Region crypto trading with Avelacom and AWS' (dated).
- **Data.** Fixtures in documented formats (synthetic values); simulations labelled.
