# 19. Cross-Region Crypto Networks — brief and source ledger

## Brief

- **Hook.** An arbitrage between a venue in Tokyo and one in Singapore is decided on the path between two cloud regions five thousand kilometres apart: over the provider's backbone, over the public internet, or over a private line bought from a specialist -- and some firms send the same message down all three and keep whichever arrives first.
- **Sections.** The hubs: Tokyo, Singapore, Hong Kong, London, Virginia; Cloud backbone, public internet and private lines; Specialised low-latency providers and virtual-server hosts; Racing the same message down several routes.
- **Defines.** Border Gateway Protocol, path inflation, cloud backbone, route racing, idempotency key.
- **Uses (defined earlier).** cloud region (B3.26), availability zone (ch16), availability-zone identifier (ch16), geodesic distance (ch10), latency floor (ch10), group index (ch10), route factor (ch10), idempotent processing (B13.24), cancel--fill race (B13.21), latency arbitrage (B11.9), dark fibre (ch13), financial extranet (ch15), instance lottery (ch17).
- **Tutorial.** Compute the geodesic floors between the five hubs, compare them with published inter-region latencies to get path inflation, then run a labelled simulation of route racing: correlated latencies on two or three routes, the distribution of the first arrival, and what the venue does with the duplicates (rejection by client order id). End state: a hub latency matrix against its floors, and the p50 and p99 of best-of-k by route mix.
- **Build.** `firm.routerace`: a multi-route sender model (routes with correlated latency draws and prices), first-arrival statistics, duplicate suppression by idempotency key with a venue-side rejection rule, and a hub latency matrix on firm.geomap with path inflation; Python. Consumed by chapter 29.
- **Weekend problem.** Three routes to Singapore -- named result: the 99th-percentile gain of racing two or three routes with correlation rho, and the price per route above which racing does not pay.
- **Facts to verify.** published inter-region latency from a cloud provider's own tool (e.g., AWS Network Manager Infrastructure Performance) or a measurement study (dated); RFC 4271 (BGP-4); specialised low-latency providers serving crypto hubs, from their own or a cloud provider's publications (dated box); venue documentation on duplicate client order ids (rejection behaviour) (dated); subsea cable routes between the hubs (TeleGeography or the cable owners) (dated).
- **Data.** Published latencies (ledger rows); simulations labelled.
