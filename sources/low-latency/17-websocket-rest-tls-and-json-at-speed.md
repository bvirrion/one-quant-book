# 17. WebSocket, REST, TLS and JSON at Speed — brief and source ledger

## Brief

- **Hook.** A crypto market maker's server sits in the same cloud region as the venue, a fraction of a millisecond away; decoding the venue's JSON depth updates and signing its own requests took longer than the network, until both moved off the hot path.
- **Sections.** HTTP, REST and connection reuse; TLS: the handshake and the record layer; WebSocket framing; JSON at speed; Signing requests off the hot path.
- **Defines.** REST interface, persistent connection, connection pool, TLS handshake, session resumption, WebSocket, WebSocket frame, structural index, request signature.
- **Uses (defined earlier).** API key (B3.15), rate limit (B3.15), request weight (B3.15), snapshot-and-delta feed (B3.26), book checksum (B3.26), cloud region (B3.26), SIMD (ch14).
- **Tutorial.** On loopback, measure a full TLS handshake against a resumed one (Python ssl, self-signed certificate made by the openssl command) and the record layer's cost per kilobyte; parse WebSocket frames (masking, fragmentation, control frames) in C++; decode a depth-update message with a structural index against a naive parser; precompute the HMAC state of a request signature. End state: a stacked budget for one websocket order -- network, TLS, framing, JSON, signing -- measured on this laptop.
- **Build.** `firm.wsclient`: WebSocket frame codec, a structural-index JSON decoder for depth updates feeding Book 3's firm.wsbook, an HMAC-SHA256 request signer checked against the RFC 4231 vectors, and a connection pool governed by Book 3's firm.ratelimit; C++20, Rust and a Python reference.
- **Weekend problem.** Cloud to venue -- named result: the share of a websocket strategy's tick-to-trade spent in decryption, JSON and signing against the network hop, and what connection reuse saves per order.
- **Data.** Synthetic depth updates in a venue-like JSON shape written by a script; measured on this laptop.
- **Facts to verify.** RFC 6455 (WebSocket); RFC 8446 (TLS 1.3: one round trip, 0-RTT); RFC 2104 and RFC 4231 (HMAC, test vectors); RFC 9110 and RFC 9112 (HTTP semantics, persistent connections); a major crypto venue's websocket and request-signing documentation (dated; see B3.15).
